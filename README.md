# RetailCore — проектная работа спринта 4

Анализ легаси и план инкрементальной трансформации платформы заказов. Подготовлено 28.10.2026 на основе учебного кейса, пяти предоставленных интервью, фрагмента Java-кода и исходной схемы. Это проектное решение; интервью с реальными сотрудниками, нагрузочные испытания и production-переключение не проводились.

**Решение:** сохранить критический write-контур Java/Oracle, сначала восстановить зависимости и наблюдаемость, затем пилотировать отдельное представление статуса и истории заказа для поддержки. После проверки данных — снять выбранную аналитическую нагрузку с Oracle и постепенно изолировать интеграции. Полная замена checkout, платёжной оркестрации и Oracle в первый этап не входит.

## Как читать доказательства

Обозначения источников: **K** — текст кейса; **B** — бизнес-спонсор; **S** — поддержка; **D1/D2/D3** — техлид, логистика, аналитика; **C** — код; **P** — исходная схема. [Реестр, ссылки и контрольные суммы](sources/README.md). В документах подтверждённые сведения отделены от гипотез, проектных решений и пробелов. Высказывание интервьюируемого — свидетельство источника, а не результат независимого технического измерения.

Недостающие SLA/SLO, RTO/RPO, p95/p99, RPS/TPS, допустимая задержка, правила деградации и консистентности не выдуманы. Их владельцы и влияние перечислены в Q-01–Q-12. Календарный план — предложение, а не обещание заказчика. До реального cutover эти вопросы должны быть согласованы.

Диаграммы — контекст с декомпозицией крупных внутренних подсистем для показа зависимостей, не deployment-схемы. PNG/SVG служат представлением; редактируемый источник — drawio. Для воспроизведения: `python tools/build_diagrams.py`, затем `python tools/validate.py`.
