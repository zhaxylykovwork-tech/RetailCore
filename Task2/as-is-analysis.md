# Восстановление AS-IS: источники, потоки и ограничения

[Редактируемая диаграмма](as-is.drawio), [представление](as-is.svg). Это расширенный контекст с крупными внутренними подсистемами, не утверждение о точном deployment или C4 L1. Крупная граница — RetailCore; партнёры и пользователи снаружи. Все источники доступны из [реестра](../sources/README.md).

## 1. Что даёт каждый артефакт

| Источник | Что устанавливает | Ограничение и дополнение к P |
|---|---|---|
| K | Цели, технологии, ресурсы/история, горизонты и запрет выдуманных требований | Нет количественных характеристик и полного списка интеграций |
| P | Java-ядро, Oracle, .NET/Python, прямые и batch/async связи, административный путь | Не эталон; не показывает полный промо/наличие, все ручные ветки и разные условия fallback |
| B/S | Бизнес-риски, недопустимость остановки, потеря прозрачности, ручные исключения | Не доказывают физический маршрут каждого запроса; нужны трассы |
| D1 | Центральная оркестрация, distributed rules, несколько writers статусов, Oracle packages, неполная корреляция | Устные сведения не дают списка tables/jobs и чисел |
| D2 | REST/broker/staging/batch, региональные и партнёрские исключения, дубли, ручные изменения | Точная семантика каждого партнёра/очереди не раскрыта |
| D3 | SQL/staging/API/CSV, разные определения статусов/скидок, ретрокоррекции и нагрузка на OLTP | Не задана полная схема витрин и экономическая модель показателей |
| C | Конкретная последовательность createOrder и SQL-стыки | Один фрагмент без реализаций Gateway/Repository/транзакций; не вся система |

## 2. Сценарий, подтверждённый кодом

1. C:55–61 создаёт объект заказа в NEW, записывает канал и регион. C:63–74 считает базовую сумму, добавляет отдельные надбавки MARKETPLACE и FAR_EAST. Числа 49/350 — детали фрагмента, не новые требования проекта.
2. C:76–88 опционально вызывает PromoService; при пустом Optional — Oracle `legacy_promo_pkg`. Нельзя вывести, что каждый timeout обработан: catch/контракт не показан.
3. C:90–96 сохраняет заказ и вставляет запись `INT_ORDER_EXPORT`. Это скрытый coupling: потребитель .NET зависит от схемы и состояния staging (D1/P).
4. C:98–105 читает правило; `requiresManualReview` даёт WAITING_MANUAL_REVIEW и ранний выход. Экспорт уже записан; надо проверить, не обрабатывает ли партнёр ещё неготовый заказ (гипотеза Q-08/12, не доказанный баг).
5. C:107–120 синхронно резервирует слот. При неуспехе выставляет DELIVERY_PENDING и пишет `RETRY_DELIVERY_QUEUE` с задержкой 10 минут. Это локальная деталь примера; не SLA доставки, не универсальная retry policy.
6. C:123–128 создаёт платежную сессию; неуспех ведёт к PAYMENT_PENDING и исключению. Слот к этому времени мог быть зарезервирован. Компенсация/откат/идемпотентность здесь не видны; это вопрос, а не доказательство их отсутствия во всей системе.
7. C:130–136 ставит CONFIRMED, затем отдельным SQL записывает sessionId и deliveryPartner. Атомарность и порядок наблюдения другими читателями неизвестны: нельзя утверждать обязательное частичное сохранение без transaction config. Созданная сессия не равна успешному списанию.

Возникающие инварианты **на согласование**: не терять принятый заказ; сохранять достоверную сумму/источник расчёта; не создавать повторный внешний эффект; не обещать подтверждение, пока его нет; ручная/batch-коррекция должна быть наблюдаема. Прямые вызовы и SQL во фрагменте подтверждены; общее время транзакций — только свидетельство D1, не замер.

## 3. Основные потоки и владельцы

| Поток | Данные и механизм AS-IS | Зависимость / риск | Источник |
|---|---|---|---|
| Каналы → Order API | Создание/изменение заказа, синхронно для сайта/моб.; канальные ветки | Изменение общего ядра затрагивает разные сценарии | P/D1/C |
| Checkout → промо/Oracle | Сумма, правила, fallback | Несовпадение расчёта при деградации, Oracle packages | D1/C:76–88 |
| Processing → логистика/платёж | Слот, платёжная сессия; sync в коде | Задержки/неизвестный исход, риск повторов | C:107–128, D2 |
| Монолит ↔ Oracle | Заказ/статусы/правила/staging/retry | Общая схема и бизнес-логика; все writers неизвестны | P/C/D1/D2 |
| Oracle staging ↔ .NET → партнёры | Запись таблицы, чтение/polling и внешняя передача | Скрытая временная связанность, повторы | P/D1/D2/C:93–96 |
| Batch/async → статусы, партнёры, аналитика | Задания, события и выгрузки | Неединые гарантии, delayed correction | P/D1/D2/D3 |
| Python/BI → Oracle и другие источники | Прямые SQL, staging, API/CSV | OLTP-конкуренция, дубли и разные определения | P/D3 |
| Оператор → Admin/Status/Oracle | Чтение и разрешённые ручные операции | Скрытые writers, нет единой истории; админку нельзя выключить вслепую | P/S/D1 |

Наличие/склады показаны как участник, известный из K/D1/D2; их конкретный API и физическая реализация не заданы. Направление отдельных callbacks и протоколы нужно подтвердить Q-08; рисунок не превращает их в факт.

## 4. Противоречия и риски

| Риск | Основание | Последствие / способ уточнения |
|---|---|---|
| R-01: неполное понимание статуса | S/D1/D3 | Ложная уверенность поддержки/клиента; Q-03/04, каталог переходов и происхождение полей |
| R-02: скрытые writers и транзакции | C/P/D1 | Пропуски событий и опасный вынос; Q-08/12, матрица таблиц/jobs + trace |
| R-03: разные промо-ветки | C/D1/B | Разная сумма/конверсия; characterization corpus, не переносить первой |
| R-04: повторный внешний эффект | D2, C:107–128 | Дубли доставки/платежного запроса; contract/идемпотентность/reconciliation Q-04 |
| R-05: общая Oracle и отчёты | K/D1/D3 | Пиковая конкуренция и сложность изменения; baseline SQL/IO, Q-02/07 |
| R-06: неполная история/lineage | S/D3 | Новый read model тоже будет вводить в заблуждение; маркировать unknown и дату начала достоверного захвата |
| R-07: ресурсов второго контура нет | K | Пилот ухудшит OLTP; capacity gate до включения snapshot/CDC |

P не опровергает интервью: неполнота схемы ожидаема. Формальный список статусов D1 не является исчерпывающей машиной состояний. Код не позволяет утверждать наличие distributed transaction, отсутствие timeout или факт бесконечных retry — эти детали остаются неизвестными.

## 5. Следствие для границ изменения

Checkout, payment orchestration, резерв, маршрут и Oracle packages остаются совместным write-контуром. Его разрезание первым имеет высокий риск и большую область воздействия. Read facade, нормализация наблюдаемых состояний и ограниченный перенос аналитического чтения позволяют получить пользу раньше, сохраняя старый маршрут. Это **проектный выбор**, не доказательство готовности CDC и полноты данных. Полный журнал причин нельзя восстановить из одних снимков строк — Q-07/08 и пробелы истории обязательны в плане.
