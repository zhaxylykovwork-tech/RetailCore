# Трансформация и промежуточное целевое состояние

Использованы три шаблона урока T: паспорт точки трансформации; матрица AS-IS → точка → TO-BE; карточка целевого состояния первого этапа. Поля шаблонов сверены на платформе 28.10.2026. [Редактируемая TO-BE](to-be.drawio), [SVG](to-be.svg). Источники/риски — Task2; требования/Q — Task1.

## 1. Выбор стратегии и альтернатив

| Вариант | Польза | Цена/риск | Решение |
|---|---|---|---|
| Полная перепись checkout и замена Oracle сразу | Сильная целевая независимость | Неизвестные правила/процедуры, общий cutover, влияние на деньги и конверсию | Отклонён для первого этапа: B/D1/K |
| Только рефакторинг внутри монолита | Меньше второго контура, полезен для seams | Не снимает всю отчётную нагрузку и разрозненность чтения | Входит как подготовка; не единственное изменение |
| Read-only Strangler: фасад чтения + независимая проекция + постепенные адаптеры | Польза поддержке, сравнение без двойных бизнес-эффектов, быстрый возврат чтения | Сложность согласованности/данных/эксплуатации, дополнительная ёмкость | Выбран условно; пилот только после Q-03/06/07/08 |

**Горизонт:** три месяца — анализ и согласование, подготовка seams и ограниченный пилот при прохождении gates. K не требует production-переезда за три месяца. Год — последовательные дальнейшие шаги по результатам пилота. Сроки реализации в roadmap — рабочее предложение, зависящее от Q-10.

### Приоритизация и что остаётся

Сначала **TP-01**: потребность S высока, side effects можно исключить, польза измерима; сложность данных средняя/высокая, поэтому только после спайка. **TP-02** использует готовые определения и извлечение, не опережает сверку. **TP-03** начинается с исследования/изоляции, production-перенос позже из-за внешних эффектов. Это качественная оценка, не придуманная финансовая эффективность.

Цена/промо, создание/резерв, платежная оркестрация, маршрутизация и финансовые статусы **сохраняются в монолите/Oracle** на первом этапе: C/D1/D2 показывают тесную зависимость и исключения. Их улучшают characterization-тестами, корреляцией, контрактами и явными границами внутри текущего контура. Админские команды остаются в старом авторизованном пути; новый интерфейс предоставляет ссылку на него, но не меняет состояние. Отказ от Oracle пока направление; перенос процедур/типов/истории потребует отдельной инвентаризации и теста совместимости, а не заявления «поменяем БД на PostgreSQL».

## 4. Шаблон 3 — карточка целевой архитектуры первого этапа

| Раздел | Предлагаемое состояние |
|---|---|
| Цель первого этапа | Проверить, сокращает ли объяснимая операторская история ручные расследования без ухудшения order flow |
| Границы | Только read-only операторское представление согласованной когорты заказов; каналы/возраст/исключения определяются после Q-08. Не клиентский checkout, не финансовое проведение, не изменение статуса |
| Основной сценарий | Заказ создаётся в текущем монолите → изменения фиксируются Oracle → проверенный capture передаёт committed changes → normalizer строит проекцию → facade выдаёт оператору историю и отметку актуальности |
| Исключения | Ручной/batch-переход, задержанный callback, частичная отмена/split, дубль/переупорядочивание, correction, неизвестный mapping, неполная старая история, отставание capture. Неизвестное маркируется и направляется на legacy/разбор |
| Компоненты | Существующие Java/Oracle/.NET/Python; новые: read facade/router, capture+normalizer, durable buffer/checkpoints, изолированное хранилище проекций, dashboard сверки. Это логические роли, не обязательные отдельные микросервисы |
| Данные/состояния | orderId + shipmentId при наличии, source transaction/position, eventId, sourceTime/capturedAt, sourceStatus и mappingVersion, normalizedState, provenance, freshness и coverageStart. Платёжный/доставочный результат не выводится из одного CONFIRMED |
| Интеграции | Существующий write-path сохранён. Oracle → capture (предпочтительно log-based CDC после Q-07) → durable buffer → projection; оператор → facade → проекция или старый read API. Направлений записи из проекции в Oracle/партнёров нет |
| Метрики | M-01–M-04 ниже; сравнение по одинаковым источникам/водяным знакам, включая исключения. Цели/окна согласуются до пилота |
| Ограничения | Ресурсы on-prem ограничены, полный лог переходов может отсутствовать, безопасность копии и восстановление должны быть подтверждены. При невозможности корректного capture stage не запускается |

## 5. Данные, надёжность и границы согласованности

**Выбор захвата:** log-based CDC предпочтителен, поскольку должен охватить приложение, batch и ручные DB-writers. Но доступность нужного режима/лицензии/PK/redo и воздействие на Oracle неизвестны (Q-07). До реализации DBA проводит capability и capacity spike. Если недоступно — не включать неполный polling под видом эквивалентного CDC. Альтернатива: ограниченный read facade над legacy без проекции, затем согласованное внедрение transaction-outbox во все точки записи; это отдельный scope и повторный gate. Пилот не блокирует работающий старый интерфейс.

**Bootstrap:** выбрать ограниченный датасет по согласованным правилам и snapshot position W0; согласованно получить текущие ORDERS, имеющуюся историю и необходимые справочники. Начать захват с W0 без разрыва и применить committed изменения до W1. Позиции и правила snapshot-overlap определяются конкретным capture; их нельзя заменить wall-clock временем. Предварительный spike доказывает отсутствие пропусков/повторов и transaction visibility. Десятки ТБ не выгружаются одним scan в пик.

**Replay:** durable buffer хранит позиции и оригинальную минимизированную запись. EventId детерминирован из источника/транзакции/таблицы/ключа/операции/позиции, не только orderId. Unique constraint/inbox и обновление проекции с checkpoint фиксируются атомарно в одной БД; ack после commit. Порядок по заказу определяется source position/версией, не временем прихода. После сбоя повтор безопасен; late correction — новое изменение с происхождением. Не обещается exactly-once внешних эффектов: у read-проекции их нет.

**Семантика:** CDC — изменения строк, не готовые бизнес-события. Normalizer сохраняет исходные значения, version mapping и связь с транзакцией; неоднозначный переход помечает UNKNOWN/needs review. Пропущенную причину не выдумывает. Полная старая timeline не гарантирована: snapshot — снимок, история только из доступных источников, coverageStart и gaps видны оператору. На refresh не смешивать несколько порядков обновления одной транзакции в «финальное» состояние.

**Ownership:** legacy остаётся источником операционного состояния и единственным writer. Проекция — производная модель чтения с eventual consistency; её freshness и допустимый lag согласуются Q-03. Нет обратной синхронизации и конкурирующих команд. При отставании/незнакомом статусе facade показывает явную неполноту и безопасный legacy read/эскалацию, не старое состояние как достоверное. Старый источник тоже может быть неполон — это отображается как неизвестность, не как «fallback всё исправил».

**Безопасность/эксплуатация:** минимальные поля без платёжных реквизитов, read-only права capture, отдельные credentials, защита канала/секретов, RBAC операторов, аудит и проверка удаления/retention по Q-06. Технология новой БД/буфера выбирается после оценки on-prem ресурсов и импортонезависимости; физическое разделение нужно подтвердить, иначе отчётная нагрузка останется на общем IO. Backup/replay и RTO/RPO проверяются до go-live. Это требования к внедрению, не отчёт об уже выполненной настройке.
